## 一、产品概述

### 1.1 一句话定义

Trae Work 助手是一款面向多账号 Trae Work 用户的桌面端管理工具，把原本散落在多个脚本中的**签到、代理捕获、账号切换、设备隔离、账号分组**能力收敛到一个简约美观的图形界面中。

### 1.2 现状与痛点

当前能力由两套独立脚本构成：

| 工具 | 位置 | 核心能力 | 交互形态 |
|---|---|---|---|
| 签到与代理模块 | `src-python/` | `auto_checkin.py` 批量签到；`device_proxy.py` MITM 代理捕获/续期 JWT + 改写设备头 | 集成到 Tauri 应用 |
| 账号切换模块 | `src-ps/` | 备份/恢复 TW 登录态、免验证码切号、重置 6 层机器码 | PowerShell 脚本（Tauri 集成调用） |

**核心痛点**：

1. **链路割裂** — 签到、切号、代理是三个独立入口，用户需记住"先装 CA → 再启代理 → 再切号点签到 → 最后跑签到脚本"的顺序。
2. **状态不可见** — JWT 何时过期、哪个账号今天签了、设备 ID 绑没绑，都要翻 JSON 和 log 文件。
3. **无分组概念** — 账号数量增长后（工作号/测试号/长期号），只能靠命名前缀区分，无法批量操作。
4. **上手门槛高** — CA 安装、代理端口、UAC 提权等概念对非技术用户不友好。

### 1.3 产品目标

| 目标 | 衡量指标 |
|---|---|
| 一体化 | 所有操作在单个应用内完成，不需要打开任何 bat/ps1 |
| 低门槛 | 首次使用 5 步内完成第一个账号接入，全程有引导 |
| 可运营 | 支持账号分组，一次操作可覆盖一组账号 |
| 可维护 | 核心逻辑仍由 Python/PowerShell 承担，UI 只做调度与展示 |
| 可演进 | v2.0 已实现 API 网关，预留账号池/积分/凭据的扩展字段 |

### 1.4 目标用户

- 持有 3~20 个 Trae Work 账号，需要每日批量签到累积积分的重度用户。
- 需要按用途区分账号（自用 / 备用 / 出租 / 测试）的运营型用户。
- 不熟悉命令行，偏好图形化操作的普通用户。

## 二、功能清单

### 2.1 本期功能（v1.0，桌面端工具）

| 编号 | 模块 | 功能描述 | 优先级 |
|---|---|---|---|
| **F01** | 环境检测 | 启动时检测 Trae Work 是否安装、是否运行、版本号；未安装则一键跳转官网引导下载 | P0 |
| **F02** | CA 证书 | 检测自签 CA 是否已装入系统根信任库；未装则提供一键安装（自动 UAC 提权） | P0 |

| **F04** | 账号捕获 | 代理开启后自动捕获 TW 发出的 JWT，按 UserID 去重，新账号自动入库并分配虚拟设备 ID | P0 |
| **F05** | 账号列表 | 展示账号名称、分组、UserID、JWT 状态、设备 ID、今日签到状态、积分 | P0 |
| **F06** | 账号分组 | 创建/重命名/删除分组；账号可拖拽或右键移入分组；按分组筛选、按分组批量签到 | P0 |
| **F07** | 批量签到 | 勾选账号或选中分组，一键执行签到；实时进度条 + 逐账号结果 | P0 |
| **F08** | JWT 续期引导 | 检测剩余有效期，临期(<24h)/过期账号高亮；点击后引导启动代理 + 切换到该账号 | P0 |
| **F09** | 登录态切换 | 选中账号一键切换 TW 登录（关闭 TW → 恢复登录态 → 启动 TW），免验证码 | P0 |
| **F10** | 设备 ID 管理 | 新增账号自动绑定虚拟设备 ID；支持查看、重置单账号设备 ID；重置前二次确认 | P0 |
| **F11** | 账号增删 | 手动新增账号（粘贴 JWT）、编辑备注名、移除账号（可选是否同时删除登录态备份） | P0 |
| **F12** | 操作日志 | 聚合代理日志 / 签到日志 / 切换日志，支持按类型、时间、关键字筛选与导出 | P1 |
| **F13** | 定时签到 | 图形化注册/卸载 Windows 计划任务，可自定义每日执行时间 | P1 |
| **F14** | 积分看板 | 展示今日新增积分、各账号累计积分、近 7 日趋势 | P1 |
| **F15** | 邀请入口 | 关于页展示「邀请注册送 5000 积分」，一键复制/打开邀请链接 | P1 |

## 三、界面设计

> 设计原则：**简约、留白、层次清晰**。采用现代桌面应用的「侧边导航 + 内容区」结构。参考界面 `gui-screenshot.png` 仅作为**功能范围**参考，不沿用其视觉样式。

### 3.1 设计语言

| 维度 | 规范 |
|---|---|
| 主色 | 深蓝紫 `#5B6CFF`（主操作）/ 青绿 `#10B981`（成功态）/ 琥珀 `#F59E0B`（警告）/ 珊瑚红 `#EF4444`（错误） |
| 中性色 | 背景 `#F7F8FA`，卡片 `#FFFFFF`，边框 `#E5E7EB`，主文字 `#1F2329`，次文字 `#8A9099` |
| 深色模式 | 背景 `#16181D`，卡片 `#1E2128`，边框 `#2A2E37`，主文字 `#E8EAED`，次文字 `#8A9099` |
| 圆角 | 卡片 12px，按钮 8px，标签 6px，头像 50% |
| 阴影 | 卡片 `0 1px 3px rgba(0,0,0,.06)`，悬浮 `0 4px 16px rgba(0,0,0,.10)` |
| 字体 | 中文 `PingFang SC / Microsoft YaHei UI`；数字/英文 `Inter`；等宽 `JetBrains Mono` |
| 间距 | 8px 基准栅格（8 / 16 / 24 / 32） |
| 图标 | Lucide 线性图标，1.5px 描边，20px 标准尺寸 |

## 六、技术方案（v1.0）

### 6.1 技术栈选型

| 方案 | 界面能力 | 包体积 | 复用现有脚本 | 开发效率 | 结论 |
|---|---|---|---|---|---|
| **Tauri 2 + React** | 优（Web 技术栈，完全还原设计稿） | 8~15 MB | 子进程调用 | 高 | ✅ **采用** |
| Electron + React | 优 | 120+ MB | 子进程调用 | 高 | 体积过大 |
| WPF / WinUI 3 | 良（需大量自定义样式） | 20~40 MB | 子进程调用 | 中 | 学习成本高 |
| PyQt / PySide | 中（拟物化困难） | 60+ MB | 原生调用 | 中 | 视觉达不到要求 |

**最终技术栈**：

```
前端：React 18 + TypeScript + Tailwind CSS + shadcn/ui + Recharts + Zustand
外壳：Tauri 2.x（Rust）
核心：Python 3.13（复用 auto_checkin.py / device_proxy.py）
切换：PowerShell（复用 trae-switch-bridge.ps1）
打包：Tauri Bundler → MSI / NSIS 单文件安装包
```

### 6.2 架构分层

│  Presentation  React + Tailwind                         │

### 6.3 核心模块实现

#### 6.3.1 TW 安装与运行检测

```rust
// 1. 安装检测：按优先级查找
//    a. 注册表 HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\*  匹配 DisplayName
//    b. %LOCALAPPDATA%\Programs\Trae\Trae.exe
//    c. %ProgramFiles%\Trae\Trae.exe
//    d. 用户手动指定路径（持久化到 app_settings.json）
// 2. 版本读取：Windows 文件版本信息 API（GetFileVersionInfo）
// 3. 运行检测：枚举进程匹配 Trae.exe
// 4. 未安装 → tauri_plugin_shell::open("https://www.trae.cn")
```

#### 6.3.2 CA 证书检测与安装

```powershell
# 检测（无需管理员）
Get-ChildItem Cert:\LocalMachine\Root | Where-Object { $_.Subject -eq "CN=TraeDeviceProxyCA" }

# 安装（需管理员，Rust 侧用 runas verb 提权）
certutil -addstore -f Root "certs\ca.cer"
```

失败兜底：弹窗提供手动安装图文步骤（双击 ca.cer → 安装证书 → 本地计算机 → 受信任的根证书颁发机构）。

#### 6.3.3 代理进程管理

```
启动：Command::new(python_exe).arg("device_proxy.py")
        .env("PROXY_PORT", port)
        .env("AUTO_CAPTURE_JWT", "1")
        .stdout(Stdio::piped())
        .spawn()

监听：独立线程逐行读 stdout → 解析日志 → emit("proxy-log", line) 推送前端
      识别 [JWT 自动更新] / [JWT 自动追加新账号] 标记 → emit("account-captured", uid)

停止：先发 CTRL_BREAK_EVENT 优雅退出，2s 未退则 TerminateProcess

健康检查：每 3s TcpStream::connect("127.0.0.1:port") 探活
端口冲突：启动前检测占用，被占用则提示更换端口
```

#### 6.3.4 签到执行

```
Command::new(python_exe).arg("auto_checkin.py").arg("--json-stream")
```

> **需对 `auto_checkin.py` 做小幅增强**：新增 `--json-stream` 参数，把每账号的结果以单行 JSON 输出（NDJSON），便于前端逐条解析渲染，而非解析中文文本。同时新增 `--accounts` 参数支持只签指定 UserID 列表（供分组/勾选场景使用）。默认不带参数时行为完全不变，保证向后兼容。

```json
{"type":"start","total":6}
{"type":"account","index":1,"user_id":"4487…","name":"清风杜宾","status":"already","credits":8200,"elapsed":0.31}
{"type":"account","index":2,"user_id":"1556…","name":"青衣网络","status":"success","delta":300,"elapsed":1.24}
{"type":"done","ok":5,"already":0,"failed":1}
```

#### 6.3.5 JWT 解析

Rust 侧实现，避免为读一个 exp 而拉起 Python 进程：

```rust
// 1. 去掉 "Cloud-IDE-JWT " 前缀
// 2. 取 payload 段，base64url 解码（补 padding）
// 3. 解析 data.id → UserID；exp → 过期时间
// 4. 计算剩余小时：正常 >24h / 临期 <24h / 已过期 <0
// 注意：不做签名校验（无公钥，且仅本地展示用途）
```

#### 6.3.6 账号切换

本项目自主实现的账号切换桥（`trae-switch-bridge.ps1`），以参数化非交互模式调用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File trae-switch-bridge.ps1 `
  -Action Switch -UserId 4487568582777872 -Json
```

- 新增 `-Action`（Switch / Save / New / Reset / List）与 `-Json` 参数。
- 以 NDJSON 输出每步进度，Rust 侧转发给前端渲染步骤条。
- 需管理员权限（重置 MachineGuid），Rust 侧统一以 runas 提权启动。

#### 6.3.7 文件监听与状态同步

```
notify crate 监听 checkin_accounts.json / device_map.json / groups.json
  → debounce 300ms
  → 重新读取并 emit("accounts-changed") 
  → 前端 Zustand store 更新，列表自动刷新
```

这样即使用户在应用外用原脚本修改了配置，界面也能实时同步。

#### 6.3.8 定时任务

```
注册：schtasks /Create /TN "TraeWorkAssistant_DailyCheckin" /TR "<exe> --silent-checkin" 
      /SC DAILY /ST 09:00 /RL HIGHEST /F
查询：schtasks /Query /TN "TraeWorkAssistant_DailyCheckin" /FO LIST
删除：schtasks /Delete /TN "TraeWorkAssistant_DailyCheckin" /F
```

应用以 `--silent-checkin` 启动时不显示窗口，直接执行签到后退出，结果写入日志并发系统通知。

### 6.4 安全设计

| 项 | 措施 |
|---|---|
| JWT 存储 | 明文存于用户数据目录（与现有脚本保持兼容）；目录权限继承用户账户；**不**随应用打包分发 |
| JWT 展示 | 界面永不完整展示 JWT，仅显示 UserID 前 4 后 4 位 |
| 日志脱敏 | 所有日志中的 JWT / device_id 一律截断为 `8391…2210` 形式 |
| 配置导出 | 导出时强制要求设置密码，使用 AES-256-GCM 加密压缩包 |
| 提权最小化 | 仅 CA 安装、机器码重置、计划任务注册三个操作提权，其余全程普通权限 |
| 更新校验 | 应用自动更新走 Tauri Updater，强制签名校验 |

## 七、v2.0 实现：本地 API 网关

> **实现说明**：v2.0.0 已完成本章全部需求。API 网关以内嵌 axum HTTP 服务实现，复用 Tauri tokio runtime，无需独立进程。所有协议适配与调度逻辑均为本项目自主设计与实现，技术栈为 Rust（axum + ureq + spawn_blocking）。

### 7.1 需求定义（G01~G03）

| 项 | 描述 |
|---|---|
| 核心目标 | 把多个 Trae Work 账号聚合成一个**本地 API 服务**，对上层应用同时暴露 OpenAI 兼容接口与 Anthropic 兼容接口 |
| 透明切换 | 根据各账号积分余额、冷却状态、分组策略，自动选号、轮转、重试；上层无需感知具体是哪一个账号、走哪一种协议 |
| 用户价值 | 在任意支持 OpenAI/Anthropic 的客户端（Cursor、Claude Desktop、自建 Agent 等）填入一个本地地址即可，无需逐账号复制 token；积分用尽自动切换，避免单号被打满 |
| 监控（G03） | 实时展示请求量、token 消耗、积分扣减、各账号健康度（冷却/错误计数） |
| 与桌面端关系 | 由 Trae Work 助手托管其生命周期（启动/停止/端口协商/账号共享），在桌面端新增「API 网关」页做状态可视化 |

### 7.2 从参考样例中提炼的"问题域信号"

仅从需求/可行性角度，参考样例提示了以下必须正视的问题（**不代表采用其实现**）：

1. **上游是私有协议**：Trae 的实际对话上游（文中称 SOLO）并非标准 OpenAI 格式，网关需要做协议翻译，而非简单转发。
2. **凭据需要可续期**：短期 accessToken 过期后若无 refreshToken 则无法自动续期，会直接导致网关停摆。
3. **需要账号池与冷却调度**：多账号并发时必须有挑号、冷却、错误隔离机制，否则极易触发平台限流。
4. **Anthropic 适配显著更难**：其 Messages API 与 OpenAI 在请求体、SSE 事件流、工具调用上差异巨大，工作量远大于 OpenAI 侧。

### 7.3 技术难点预判（从原理出发）

#### 难点 1：可续期凭据的获取 ★★★★★（最高，核心阻塞点）

| 维度 | 本期 v1.0 捕获的凭据 | 网关所需的凭据 |
|---|---|---|
| 内容 | 仅 `accessToken`（Cloud-IDE-JWT） | `accessToken` + 可续期的 `refreshToken` + 过期时间 + 设备身份 |
| 有效期 | 约 13 天，过期后**无法自动续期** | 需能在本地无限续期 |
| 获取方式 | MITM 代理捕获请求头 | 需走登录授权链路（拿到 refreshToken） |
| 设备身份 | 伪造 `x-device-id` | 需与账号绑定的稳定设备标识 |

**问题本质**：v1.0 的 MITM 代理只能截获 HTTP 请求头里的 `accessToken`，**拿不到 `refreshToken`**（它不在请求头里，只存在于客户端本地）。没有 `refreshToken` 就无法自动续期，网关会周期性停摆。

**候选方案**（均在 v2.0 立项时评估，与参考样例思路一致但独立实现）：

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 登录授权闭环**（推荐） | 桌面端内嵌 WebView 打开登录页 → 拦截本地回调 → 解析 refreshToken → 换取 accessToken | 拿到完整可续期凭据；体验好（无需复制粘贴） | 依赖登录页结构，上游改版需跟进 |
| B. 读取本地存储 | 从 TW 的 `state.vscdb` / Local Storage 直接读取 refreshToken | 无需重新登录 | 需解密，存储结构可能变化，不稳定 |
| C. 代理捕获增强 | 扩展 MITM 代理，伺机拦截 token 刷新请求/响应，从中捕获 refreshToken | 复用现有代理 | 刷新触发频率低（约 13 天一次），捕获窗口极窄 |

**结论**：以 **A 为主**（新增账号走登录授权），**C 为辅**（已有账号在代理运行期间伺机捕获），B 作实验性兜底。凭据模型以**新增独立文件**承载（见 5.1 扩展提示），不污染 v1.0 数据结构。

---

#### 难点 2：Anthropic 协议适配 ★★★★☆

v1.0 及网关初版以 OpenAI 兼容为主。Anthropic Messages API 与 OpenAI 差异显著：

**请求层差异**：

| 项 | OpenAI | Anthropic |
|---|---|---|
| 端点 | `POST /v1/chat/completions` | `POST /v1/messages` |
| 鉴权头 | `Authorization: Bearer <key>` | `x-api-key: <key>` + `anthropic-version: 2023-06-01` |
| system | `messages[0].role = "system"` | 顶层 `system` 字段（字符串或 block 数组） |
| max_tokens | 可选 | **必填** |
| content | 字符串 或 `[{type:"text"...}]` | 必须是 `[{type:"text"|"image"|"tool_use"|"tool_result"}]` |
| 工具定义 | `tools[].function.{name,description,parameters}` | `tools[].{name,description,input_schema}` |
| 工具调用 | `message.tool_calls[].function.{name,arguments}` | `content[].{type:"tool_use",id,name,input}` |
| 工具结果 | `role:"tool"` + `tool_call_id` | `role:"user"` 中 `content[].{type:"tool_result",tool_use_id,content}` |
| 停止原因 | `finish_reason` | `stop_reason` |

**流式 SSE 差异**（工作量主要在此）：

```
OpenAI：单一事件类型，增量在 choices[0].delta
  data: {"choices":[{"delta":{"content":"你"}}]}
  data: [DONE]

Anthropic：多种事件类型，需维护 content block 索引状态机
  event: message_start        → 初始化 usage
  event: content_block_start  → 新 block（text / thinking / tool_use）
  event: content_block_delta  → 增量（text_delta / thinking_delta / input_json_delta）
  event: content_block_stop   → block 结束
  event: message_delta        → stop_reason + output_tokens
  event: message_stop         → 流结束
  （穿插 event: ping 心跳）
```

**额外复杂点**：
- **思考链**：上游若返回 `reasoning_content`，在 Anthropic 侧应映射为 `thinking` 类型 block，需独立的 block 索引管理。
- **工具调用流式**：Anthropic 的 `tool_use` 通过 `input_json_delta` 分片传输，需累积拼接；上游若整块下发则需反向切分。
- **token 计数**：Anthropic 在 `message_start` 即需 `input_tokens`，但上游用量事件往往在流末才到，需要预估或在末尾修正。

**实现建议（架构层面，非代码）**：引入**中间表示层（IR）**，避免 N×M 转换爆炸：

```
OpenAI Request   ─┐                    ┌─→ OpenAI SSE
                  ├─→ IR ─→ 上游 ─→ IR ─┤
Anthropic Request─┘                    └─→ Anthropic SSE
```

#### 难点 3：积分感知的调度策略 ★★★☆☆

网关不能简单"挑积分最高的账号一直打"，存在三类问题：
1. **积分不实时** — 积分只在签到或主动查询时更新，请求中不会实时扣减，高并发会把流量集中到同一账号直至触发限流。
2. **无分组隔离** — 无法实现"生产流量走 A 组、测试流量走 B 组"。
3. **无成本模型** — 不同模型、不同上下文长度消耗积分不同，无法预估。

**改进设计**：

```
积分本地账本（Credit Ledger）
├─ 基准值：签到/查询接口返回的真实积分
├─ 预扣：每次请求前按模型 × 预估 token 预扣，失败则回滚
├─ 校准：每 N 次请求或每 M 分钟主动查一次真实积分，覆盖本地估算
└─ 阈值：低于阈值自动降权（不禁用，排到队尾）

调度策略（可配置）
├─ credit_first  积分最高优先（适合"用完一个换一个"）
├─ round_robin   均衡轮询（适合"平摊消耗，延长整体寿命"）
├─ weighted      按积分加权随机（避免热点集中）
└─ group_first   优先使用指定分组，耗尽后回落备用组

冷却状态机（设计思路）
├─ 权益不足 → 长冷却
├─ 限流(429)/未找到(404) → 短冷却
├─ 连续错误 ≥ 阈值 → 中冷却
├─ 会话失效(401) → 禁用，需重登
└─ 签到后自动解冻
```

#### 难点 4：桌面端与网关进程的集成 ★★★☆☆

网关作为独立服务运行时，桌面端需解决：

| 问题 | 设计方向 |
|---|---|
| 技术栈 | v2.0 立项时再定（Go/Python/Rust 均可），打包为独立可执行文件，由桌面端以**子进程**方式托管 |
| 进程生命周期 | 桌面端启动网关、退出时确保终止（Windows 用 Job Object 防孤儿进程） |
| 配置传递 | 通过环境变量传入，避免额外配置文件；网关 API Key 由桌面端随机生成并安全保存 |
| 端口管理 | 默认端口 + 冲突自动探测可用端口，回写设置并展示 |
| 账号共享 | 网关直接读取桌面端数据目录中的账号/凭据文件，双方共享同一份数据 |
| 状态可视化 | 桌面端轮询网关健康/状态接口，渲染各账号积分、冷却剩余、错误计数 |

> 注意：此处的“进程管理”是通用模式，适用于任何内嵌服务。

#### 难点 5：上游私有协议的隐藏约束 ★★★☆☆

从参考样例对其上游 payload 的处理中，可归纳出上游若干"反常规"约束，无论用什么技术栈实现都**必须保留**：

| 约束 | 说明 |
|---|---|
| `tool_choice` / `parameters` 形态特殊 | 部分字段在 OpenAI 标准中是 object，上游要求为字符串或特定结构，需做映射 |
| assistant 工具调用字段名不同 | 字段名与标准不一致，空 name 条目可能导致上游反序列化失败，必须剔除 |
| `content` 必须是数组 | 字符串 content 需包装为 `[{type:"text",text:...}]` |
| 强制流式 | 上游可能只支持流式响应，非流式需网关侧聚合模拟 |
| 必须携带设备标识 | 与账号绑定的 `X-Machine-Id` / `X-Device-Id` 缺失会被风控 |

这些约束在 OpenAI 与 Anthropic 两条通路适配时**同样适用**（因为最终都落到同一上游）。

| 风险 | 等级 | 影响 | 应对 |
